Simulator Field Manual

A discrete-event simulation for studying dynamic workforce allocation under changing demand, disruption and uncertainty — configured, for now, as a Chennai-division subset of Southern Railway.

Not a digital twin

Station and train names are real; every operational number is invented. No IRCTC or Indian Railways data is used at runtime, and none is required. This is a plausible synthetic world for studying allocation mechanisms — read every figure below as a property of the model, not a claim about the real railway.

01

Overview

Work exists in this simulator because something happened — a train ran late, a platform got crowded, a signal failed. Nothing is drawn from a fixed task list.

The engine is a SimPy discrete-event simulation. Passenger demand is generated from a latent process and allocated under capacity constraints; that allocation determines station workload; workload becomes tasks; tasks compete for a heterogeneous, constrained workforce; disruptions inject further tasks through the same machinery as routine work, so a delay can cascade into cleaning and ticketing backlogs exactly as it would in practice. One SimulationEngine instance is the whole world for one episode.

The causal chain

Every stage feeds the next causally. Demand is never summed from confirmed + RAC + WL + unreserved + platform tickets — those are outputs of one capacity-constrained process, not independent draws.

Mental model

Formally: task execution is a semi-Markov decision process. The clock advances freely between decision epochs — a task becomes assignable, a worker frees, a shift boundary arrives — and something (currently a rule-based policy, see §5) must act only at those epochs.

02

Core concepts

The engine is domain-agnostic: none of these types mention railways. Southern Railway is a configuration layered on top — see §11.

Worker
A heterogeneous resource: skills (proficiency per skill, 0–1), qualifications, fatigue, hourly_cost, absence_propensity. Two workers in the same role are not interchangeable.
Task
One activity instance: a required skill and minimum proficiency, required qualifications, a priority, a deadline, and a lognormal duration. Belongs to a case_id.
Process
A directed graph of activities (simulation/processes/templates.py). Completing an activity spawns its successors; some activities can loop back on rework instead of closing.
Decision epoch
A point where the driving policy must act. Two kinds: DISPATCH (a task is assignable) and STAFFING (a shift boundary — hold, activate a reserve, authorise or release overtime).
Eligibility
Hard feasibility: on shift, not absent, qualifications ⊆ worker's, proficiency ≥ minimum, travel distance ≤ limit. Enforced as an action mask, never as a reward penalty.
Disruption
A self-exciting point-process event (asset failure, train delay, demand spike) that spawns real tasks through the same process graphs as routine work — see §9.
True state / observation
Latent quantities (simulation/state/true_state.py) the engine tracks but never exposes, versus the noisy, delayed, sampled instruments the policy actually reads — see §10.

The Gymnasium wrapper and the three rule-based drivers (random, greedy, wfm_heuristic) exist because the simulation needs something to make dispatch and staffing decisions in order to run at all. 04

How data is generated

There is no separate batch dataset builder. Every run generates its data live, in this order, and you export whichever view of it you need afterwards.

The generation order

1 · Config
Domain + scenario YAML load into typed objects (DomainConfig, ScenarioConfig).
2 · RNG streams
RNGRegistry(seed) derives 14 independent named streams (demand_latent, workforce_absence, disruption_severity, …) so a draw in one subsystem never shifts another's.
3 · Population
build_workforce() draws ~338 workers (role, per-worker skill noise, cross-training, cost, experience, absence propensity, demand-weighted shift); build_reserve_pool() clones a ~12% activatable reserve.
4 · Assets
Per-station, per-tier equipment (signals, track circuits, escalators, lighting, coach rakes) that can fail and need repair.
5 · Demand
Each simulated day, DemandModel computes an AR(1)-correlated latent intensity per train/class, draws negative-binomial gross demand, and allocates it into confirmed/RAC/waitlist by capacity (§8). Footfall is drawn hourly per station from a shared pressure factor.
6 · Tasks
Departures spawn turnaround cases; footfall spawns ticketing and, above a pressure threshold, crowd_response cases; a daily programme spawns maintenance inspections. Each case unfolds through its process graph.
7 · Disruptions
A Hawkes point process per station per disruption type is thinned each simulated hour; accepted draws spawn emergency_repair or crowd_response cases through the same process engine (§9).
8 · Execution
The driving policy claims workers at decision epochs; task duration is drawn lognormal, scaled by proficiency and fatigue.
9 · Feedback
Completed customer-facing tasks compute a latent experience value and sparsely, with delay, sample a CSAT/NPS response (§10). Performance is cut at shift boundaries.
10 · Logging
Every activity start/end and every narrative event (a delay, a failure, a staffing action) is appended to EventLog and KPIAccumulator as it happens.

Getting a dataset out of a run

A "dataset" is what you export from engine after a run. There is no separate CLI for this — run a scenario, then pull whichever view you need:

# run_sim.py's --trace flag does step 3 below for you automatically
from rl.environment.env_a import WorkforceEnvA
from rl.policies.baselines import build_policy

env = WorkforceEnvA(scenario="normal_weekday", seed=0)
policy = build_policy("wfm_heuristic")
obs, _ = env.reset(seed=0)
while True:
    obs, r, term, trunc, info = env.step(policy.act(obs, env.action_masks(), env))
    if term or trunc: break

# 1. PM4Py-compatible event log
env.engine.log.to_dataframe().to_csv("event_log.csv", index=False)
env.engine.log.to_xes_dataframe().to_csv("event_log_xes.csv", index=False)

# 2. KPIs, costs, observed feedback, latent ground truth (validation only)
env.engine.kpis.summary()
env.engine.outcome_summary()

# 3. Planned roster / schedule entries
env.engine.roster.to_records()

Running it

Every command below runs from the project root, with the virtual environment already built.

Setup

python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

Run one simulated day and watch it

.venv/bin/python -m experiments.runners.run_sim \
    --scenario normal_weekday --policy wfm_heuristic --seed 0 --trace out/run.json

Prints an interleaved event timeline (cascades marked) and the KPI summary. Open viz/index.html, click Load trace, pick out/run.json: a play/scrub clock, live station queues, department load, the event feed, the decision log, and the CSAT/NPS/cost panel.

Compare policies across scenarios

.venv/bin/python -m experiments.runners.run_baselines \
    --scenarios normal_weekday,high_demand,combined_stress \
    --policies random,greedy,wfm_heuristic --seeds 5

Check the world is behaving

.venv/bin/python -m analysis.validation.validate --scenario normal_weekday --seed 0
.venv/bin/python -m analysis.validation.diagnose  --scenario normal_weekday --policy greedy

validate separates invariants (a failure is a bug) from plausibility (a failure is miscalibration). diagnose explains why a run looks the way it does.

Tests

Seeds & reproducibility

Everything that looks random — demand, workers, absences, failures, task durations — is really one deterministic sequence of numbers, unrolled from a single starting integer. Same seed, same world, every time.

A seed is the starting state for a pseudo-random number generator. Nothing here is "truly" random; --seed 0 and --seed 1 each unroll into their own long, fixed sequence of draws, and the simulator just consumes numbers from that sequence as it goes. Same seed, same scenario, same policy ⇒ the exact same sequence of decisions is offered and the exact same world plays out — byte-identical output, not just "similar."

One seed does not feed a single global generator. RNGRegistry (simulation/core/rng.py) derives 14 independent named streams from it, one per subsystem, by hashing "<seed>:<stream_name>" with SHA-256:

demand_latent · demand_booking · demand_unreserved
workforce_population · workforce_absence · workforce_fatigue
process_duration · process_rework
disruption_base · disruption_hawkes · disruption_severity
observation_noise · regime · policy
Why it's split into 14 streams

Adding one extra random draw to the workforce generator does not shift a single demand number, because they live in different streams entirely. This is what makes paired-seed comparison valid: on the same seed, two different policies face identical demand, absences and disruptions, so any KPI difference is attributable to the decisions, not to an accidental change in the world underneath them.

How to use it

GoalWhat to change
Reproduce a run exactlyDon't change anything — --seed defaults to 0, so re-running the identical command reproduces the identical out/run.json
Get a different worldPass a different integer: --seed 1, --seed 42, anything — no value is "special"
Compare two policies fairlyHold --seed fixed, vary --policy, then load both traces into the visualiser's Compare panel
Get a statistically defensible answerSweep seeds with run_baselines.py --seeds N (runs 0..N-1) and read the mean ± 95% CI, not a single run
Change a scenario's default seedEdit scenario.seed in that scenario's YAML — only takes effect when --seed is omitted on the command line
 
# same command, same seed (0, the default) -> identical file
run_sim.py --scenario normal_weekday --policy wfm_heuristic --trace out/a.json
run_sim.py --scenario normal_weekday --policy wfm_heuristic --trace out/b.json
diff out/a.json out/b.json          # -> no output: identical

# same command, different seed -> a different but equally valid world
run_sim.py --scenario normal_weekday --policy wfm_heuristic --seed 1 --trace out/c.json
diff out/a.json out/c.json          # -> differs, as expected

# fair A/B: hold the seed, vary the policy
run_sim.py --scenario normal_weekday --seed 7 --policy greedy        --trace out/greedy.json
run_sim.py --scenario normal_weekday --seed 7 --policy wfm_heuristic --trace out/heuristic.json

# statistical confidence: 5 seeds (0-4), mean +/- 95% CI per metric
run_baselines.py --scenarios normal_weekday --policies greedy --seeds 5
What seed does not control

Scenario difficulty — the demand multiplier, absence rate, disruption rates — lives in the scenario YAML (§7), not in the seed. The seed only picks which random draw you get of whatever difficulty that YAML specifies; it cannot make normal_weekday behave like combined_stress.

08

Demand & booking

Waitlist is emergent from capacity, never an independent draw.

One demand pool exists per (train, class, day). Bookings are allocated first-come, first-served: positions 1…C become confirmed, the next rac_fraction × C become RAC, everyone past that is waitlisted. An aggregate cancellation rate then frees berths, promoting RAC → confirmed and waitlist → RAC in order. Demand is never the sum of confirmed + RAC + WL + unreserved + platform tickets — those are outputs of one process, not independent variables.

Unreserved demand, platform tickets and general footfall all load on a shared "station pressure" AR(1) factor with their own base rates and idiosyncratic noise, so they are correlated but not redundant.

rac_fraction0.08RAC buffer as a share of berth capacity

Validated

On the reference scenario: demand variance/mean ratio 6.07 (overdispersed as intended); 9 of 40 train-class combinations produce a waitlist under normal load, rising sharply under combined_stress (869 → 3,681 waitlisted passengers/day).

09

Disruptions & cascades

A failure raises the short-term rate of further trouble. There is no separate "disruption handler" — disruptions spawn ordinary tasks.

Each (station, disruption type) pair runs a Hawkes point process: λ(t) = μ + Σ weight·branching_ratio·β·exp(−β·(t−tᵢ)). It is parameterised by branching ratio — the expected number of direct offspring per event — validated < 1 at construction, because a process at or above that threshold is non-stationary and explodes. Neighbouring stations receive damped, weighted excitation, so network spread cannot push the aggregate ratio over the stability threshold either.

An accepted draw spawns an emergency_repair or crowd_response case through the same process engine as routine work, so delay → crowding → extra commercial and cleaning work → knock-on delay emerges from the mechanics.

Failure mode, corrected

An early build parameterised excitation directly by alpha with unbounded neighbour history — the process was supercritical and produced 2,770 disruptions in one simulated day. Reparameterising on branching ratio (with a hard validation check) fixed it: the reference scenario now produces 19 disruptions/day, 3 of them cascades.

Latent state vs. observation

The separation is structural, not a convention. FeedbackRegistry.observed() filters on delivery time, not interaction time — a response cannot be seen before it arrives. Performance aggregates only closed review periods.

Validation & tests

Two tiers, deliberately kept apart.

  • Invariants — things that must never happen. A failure is a bug: capacity exceeded, double-booked workers, a qualification violated, an undelivered survey visible to the policy.
  • Plausibility — statistical properties a realistic world should have. A failure means miscalibration, not a bug: weekly seasonality, demand overdispersion, duration skew, a sub-critical disruption process.

Known limitations

  • Every rate, cost and probability not traceable to a public aggregate is invented. This world is about mechanism, not Southern Railway's real numbers.
  • The booking model is deliberately lean: aggregate cancellation and promotion, no per-passenger cancellation hazard, no chart preparation, no GNWL/TQWL sub-quotas.
  • Overall utilisation reads moderate while specific skills bottleneck — realistic (specialists are scarce, generalists idle), but it means the aggregate number understates local pressure.
  • Observability is near-complete apart from the feedback layer; the latent/observed seam exists so a fuller POMDP variant can be added without restructuring the generative model.
  • No learning is implemented. The Gymnasium wrapper and rule-based policies exist to drive the simulation, not to demonstrate an RL result.

Southern Railway (Chennai division subset) is the initial domain configuration, not the architecture — see §3 and §11. Source of record: this repository's README.md and RESEARCH_REPORT.md.
